## 1. 背景与问题定义

### 1.1 问题陈述

企业招聘存在两个核心矛盾：

| 现状痛点 | 影响 |
|---|---|
| HR 逐一阅读简历，凭印象打分，无结构化证据 | 评分不一致、遗漏关键信息、候选人体验差 |
| JD 笼统模糊，面试官无法基于同一标准提问 | 面试质量参差不齐，决策难以追溯 |
| 简历筛选占用 HR 60% 以上精力，低价值重复劳动 | 关键职位招聘周期长，人才流失 |
| AI 工具直接给出录用/淘汰结论，缺乏透明度 | 合规风险、偏见风险、HR 不信任工具 |

### 1.2 核心假设

> **假设**：如果 AI 能把"我为什么给这个分"这件事解释清楚，并把最终决定权留给 HR，HR 的接受度和信任度会显著提升。

验证方式：通过演示链路收集 HR 反馈；观察 HR 是否修改 AI 分数、修改频率和方向。

### 1.3 设计原则

1. **证据驱动**：每一个评分背后必须有简历原文引用，不允许"综合判断"类模糊结论
2. **人工兜底**：系统永远不自动录用或淘汰候选人，只产出推荐、给出判断依据
3. **可追溯**：所有 Agent 调用、分数来源、HR 修正均记录，支持事后审计
4. **隐私最小化**：简历原始文件不落库，发送给模型前自动脱敏手机、邮箱、身份证号

## 2. 目标用户与场景

### 2.1 核心用户

| 角色 | 使用场景 | 核心诉求 |
|---|---|---|
| **招聘 HR**（主用户）| 岗位发布 → 简历筛选 → 面试安排 | 快速过滤、结论可信、能向业务方解释 |
| **用人部门负责人** | 审核 HR 推荐结果、参与面试设计 | 面试题精准、候选人差距一目了然 |
| **AI 产品/算法团队**（内部）| 评估 Agent 表现、优化 Prompt | 可量化的评测指标、可复现的测试集 |

### 2.2 典型用户旅程（Happy Path）

```
1. HR 粘贴 JD 文本
      ↓ AI 解析 → 岗位能力模型（5-10 项要求，权重合计 100）
2. HR 调整权重（可选）
      ↓
3. HR 上传候选人简历（PDF / TXT）
      ↓ AI 解析简历 → 结构化简历 Profile
      ↓ AI 证据匹配 → 逐项评分 + 原文引用 + 差距清单
4. HR 查看候选人排序，点击进入详情
      ↓
5. HR 生成面试题（基于差距和风险项）
      ↓
6. HR 运行候选人模拟回答（可选，用于演示或内部培训）
      ↓
7. AI 评估模拟回答，产出面试报告
      ↓
8. HR 下载/分享报告，做最终决定
```

### 2.3 非目标用户

- 猎头（批量外发，与系统定位不符）
- 候选人自助（当前版本不对 C 端开放）

## 3. 产品范围与边界

### v1 范围（已交付）

| 功能模块 | 说明 |
|---|---|
| JD 结构化解析 | 将自然语言 JD 转为带权重的能力模型 |
| 简历解析 | PDF/TXT 提取，结构化为 Profile |
| 人岗匹配 | 逐项证据匹配，0-100 评分，总分由客户端加权计算 |
| 面试题生成 | 基于差距和风险项，输出 6 道结构化面试题 |
| 模拟回答 | 基于简历事实生成候选人模拟回答（演示用） |
| 面试评估 | 逐题 STAR 评分，产出推进建议 |
| 演示模式 | 内置 3 个岗位 × 6 位候选人稳定演示数据 |
| 离线评测 | 30 条测试案例，含边界 + 公平性反事实测试 |

### v1 明确不做

- 用户登录与 RBAC（权限管理）
- 多候选人持久化对比（仅支持单候选人完整链路）
- 自动发送拒信或邀约邮件
- 与 ATS（招聘系统）对接
- 简历数据库搜索
- 数据库加密与审计日志

## 4. 功能需求

### 4.1 JD 解析（F-01）

| 需求 ID | 描述 | 优先级 |
|---|---|---|
| F-01-01 | 输入：任意格式 JD 文本；输出：title、summary、requirements（3-10 项）、ambiguities | P0 |
| F-01-02 | 每项要求包含：id（英文短标识）、label、detail、weight（整数）、kind（必备/加分） | P0 |
| F-01-03 | 权重合计必须等于 100，由应用层校验（不依赖 AI 自行保证） | P0 |
| F-01-04 | HR 可在 UI 调整每项权重，调整后实时重算总分 | P1 |
| F-01-05 | 模型不得引入 JD 中没有依据的硬性门槛 | P0 |

### 4.2 简历解析（F-02）

| 需求 ID | 描述 | 优先级 |
|---|---|---|
| F-02-01 | 支持 PDF（pdfjs 客户端提取文本）和 TXT 格式 | P0 |
| F-02-02 | 简历原始文件不写入数据库，服务端即时提取即时丢弃 | P0 |
| F-02-03 | 提取前对手机号、邮箱、身份证号做正则替换脱敏 | P0 |
| F-02-04 | 模型只提取明确事实，无法确认的放入 missingInformation | P0 |
| F-02-05 | 批量简历支持：同一岗位可导入多份简历，系统维护批次状态 | P1 |

### 4.3 人岗匹配（F-03）

| 需求 ID | 描述 | 优先级 |
|---|---|---|
| F-03-01 | 逐一评价每个 requirement，给出 status（已满足/部分满足/待验证/不满足）+ score（0-100） | P0 |
| F-03-02 | evidenceQuote 必须是简历原文连续片段，不得改写拼接；无证据时为空字符串 + "待验证" | P0 |
| F-03-03 | 总分 = Σ(score × weight / 100)，由客户端计算（不信任模型直接给总分） | P0 |
| F-03-04 | 必备项未满足、核心能力缺失时，系统触发人工确认保护，推荐结论不得为"推荐面试" | P0 |
| F-03-05 | HR 可修正单项分数，修正后记录 scoreSource = "HR修正" | P1 |

### 4.4 面试题生成（F-04）

| 需求 ID | 描述 | 优先级 |
|---|---|---|
| F-04-01 | 生成 6 道不重复面试题，优先覆盖高权重要求、差距项和风险项 | P0 |
| F-04-02 | 每题包含：type（经历追问/能力验证/情景问题/风险核验）、skill、question、rationale、relatedRequirementId | P0 |
| F-04-03 | 禁止涉及年龄、婚育、健康、民族等与胜任力无关信息 | P0（合规硬约束） |

### 4.5 演示与评测（F-05）

| 需求 ID | 描述 | 优先级 |
|---|---|---|
| F-05-01 | 演示模式使用预计算结果，不消耗 API，可离线运行 | P0 |
| F-05-02 | 离线评测脚本可独立运行，输出 JSON + Markdown 报告 | P1 |
| F-05-03 | 评测包含稳定性复测（同一案例运行 3 次）和公平性反事实测试 | P1 |

## 5. 非功能需求

| 类别 | 要求 |
|---|---|
| **响应时间** | 单候选人完整链路（JD解析+简历解析+匹配）≤ 20 秒（P50） |
| **可靠性** | 模型失败自动重试 1 次；结构校验失败自动修复重试 1 次 |
| **可扩展性** | AI_BASE_URL 可配置，支持私有化部署或企业 API 网关切换，无需改代码 |
| **类型安全** | 全链路 TypeScript + Zod Schema 校验，模型输出不得绕过校验直接使用 |
| **可测试性** | 核心业务逻辑单元测试覆盖；Agent 链路有离线评测集 |

## 6. Agent 设计约束

> 这是 v1 区别于普通 AI 工具的核心设计决策，详见 [Agent 架构设计文档](../agent-design/multi-agent-architecture.md)。

1. **不允许幻觉引用**：evidenceQuote 的可定位性是核心质量指标，引用定位率目标 ≥ 95%
2. **分数与证据分离**：模型给单项分数（0-100），加权总分由应用层计算，防止模型"直接给结论"
3. **推荐结论枚举**：只有「推荐面试」「待人工确认」「暂不推荐」三种，不允许模糊表述
4. **温度控制**：所有 Agent 调用 temperature=0.1，追求稳定可复现
5. **JSON 输出 + Zod 校验**：强制结构化输出，失败自动修复重试一次

## 7. 数据与隐私边界

```
简历文件（PDF/TXT）
  → 服务端提取文字 → 即时丢弃文件
  → 脱敏（手机、邮箱、身份证、姓名标注段）
  → 发送模型 → 模型返回结构化 Profile
  → 写入数据库（脱敏后文本 + 结构化字段）
  → 原始文件永不落库
```

**v1 不保证的隐私项**（需 v2 补充）：
- 数据库静态加密
- 字段级查看权限（RBAC）
- 数据保留期限自动清除
- 审计日志

## 8. 成功指标

### 8.1 Agent 质量指标（已有评测结果）

| 指标 | v1 目标 | 实测结果 |
|---|---|---|
| 工作流成功率 | ≥ 95% | **100%** |
| 引用定位率 | ≥ 90% | **95.7%** |
| 无证据高分率 | = 0% | **0%** |
| 匹配档位符合率 | ≥ 70% | **73.3%** |
| 稳定性（3次复测推荐一致） | 100% | **100%** |
| 公平性（姓名/学校反事实差分） | 分数差 ≤ 5 | **最大差 4** |
| 平均链路耗时 | ≤ 20s | **13.3s** |

### 8.2 待验证指标（需真实场景数据）

| 指标 | 说明 |
|---|---|
| HR 分数修正率 | HR 修改 AI 分数的频率，反映 AI 可信度 |
| 招聘周期缩短率 | 对比使用前后 HR 简历筛选耗时 |
| 面试通过率提升 | 进入终面的候选人质量是否提升 |

## 9. 迭代路线

### v1（已交付）
单岗位单候选人完整链路 + 演示模式 + 离线评测

### v2（规划中）
- 多候选人持久化对比（批次管理）
- HR 分数修正 + 修正记录
- 用户登录（单机本地账号，不依赖云服务）
- 候选人状态流转（待筛选 → 推荐面试 → 已面试 → 已录用/淘汰）

### v3（探索）
- 企业 RBAC + 审计日志
- ATS 集成（Webhook 推送）
- 多轮面试追踪
- 数据库加密

## 10. 开放问题

| 问题 | 背景 | 决策建议 |
|---|---|---|
| 是否支持视频/音频简历？ | 技术可行，但提取质量低，噪音大 | v2 不做，等多模态模型成熟 |
| HR 修正分数后是否重新触发 Agent？ | 修正可能使匹配结论失效 | 修正只更新显示，不重新 Agent，由 HR 判断是否重跑 |
| 候选人档案是否应对候选人本人开放？ | GDPR/个人信息保护法要求 | v1 不涉及，v3 合规版本需要 |
| 评测集扩展频率？ | 30 条覆盖了常规+边界+公平性 | 每季度更新，重点补充 Badcase |
