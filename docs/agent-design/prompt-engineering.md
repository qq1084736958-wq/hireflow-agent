# Prompt 工程设计文档

> 关联：[多 Agent 架构](./multi-agent-architecture.md)

本文记录 HireFlow 各 Agent Prompt 的设计思路、关键选择和已知局限，供后续迭代参考。

---

## 1. Prompt 设计原则

| 原则 | 具体做法 |
|---|---|
| **角色单一** | 每个 Agent 只扮演一个专业角色，不让单个 Prompt 承担多种职责 |
| **约束显式化** | 把"不能做什么"写得比"要做什么"更详细，因为模型更容易遗漏禁止项 |
| **输出结构优先** | System Prompt 直接给出 JSON Schema hint，减少格式歧义 |
| **举例胜于描述** | 关键约束给正反例（✅/❌），比规则描述更有效 |
| **温度控制** | temperature=0.1，招聘评分不需要创意，需要稳定 |

## 2. 各 Agent Prompt 分析

### 2.1 JD 解析 Agent

```
你是企业内部招聘团队的岗位分析 Agent。
将 JD 转换为清晰、可评分的能力模型。
合并含义相近的条件，只保留 5 到 10 项最关键要求，不得超过 10 项。
要求应互不重复，权重合计 100。
不要引入 JD 中没有依据的硬性门槛。
```

**设计亮点：**
- "只保留 5-10 项最关键要求"：防止模型列出 20+ 项细碎要求，导致权重分散
- "不要引入 JD 中没有依据的硬性门槛"：防止模型凭印象加入"本科以上学历"等隐性条件
- "权重合计 100"：写进 Prompt 是第一道防线，Zod 校验是最终兜底

**已知局限：**
- 当 JD 本身描述模糊时（如"有 AI 经验"），模型倾向于拆得过细
- 中英文混合 JD 有时导致 id 字段使用中文，需要在 Zod 校验中处理

---

### 2.2 简历解析 Agent

```
你是简历分析 Agent。
只提取简历明确提供的信息。
不得补写公司、项目、职责或成果。
无法确认的信息放入 missingInformation。
```

**设计亮点：**
- "只提取明确提供的信息"配合"不得补写"：双重否定强化约束
- `missingInformation` 字段：为缺失提供明确出口，避免模型用猜测填充

**迭代记录：**

v0 Prompt 没有 missingInformation 字段，导致模型用"可能有..."填充，产生幻觉。
加入字段后，模型有了"有地方放不确定信息"的出口，幻觉率显著下降。

**已知局限：**
- 非标准简历格式（如纯图片 PDF）在 pdfjs 提取阶段就失效，与 Prompt 无关
- 极短简历（< 100 字）时模型仍倾向于推断，需要 Harness 边界用例覆盖

---

### 2.3 证据匹配 Agent（最复杂）

```
你是证据驱动的人岗匹配 Agent。
逐项评价岗位要求，只能引用给定简历中连续存在、可逐字定位的原文片段，
不得概括、拼接、改写或补全为引用。
evidenceQuote 必须能直接在简历原文中搜索到；
没有直接原文时必须返回空字符串并使用"待验证"，
不得把缺失信息当作明确不满足。
不得仅因出现"AI"等关键词就推断候选人具备对应经验。
分数范围 0-100。
```

**关键约束逐条分析：**

| 约束 | 为什么需要 | 效果 |
|---|---|---|
| "可逐字定位的原文片段" | 防止模型概括改写，制造幻觉引用 | 引用定位率 95.7% |
| "不得仅因关键词就推断经验" | 很多简历写"使用 ChatGPT"≠ AI 产品经验 | 无证据高分率 0% |
| "不得把缺失信息当作不满足" | 简历未写不代表没有；需要面试验证 | 减少误判低档位 |
| `status: "待验证"` 显式选项 | 给模型"我不确定"的出口 | 减少强行给结论 |

**正反例设计（内嵌于 Schema Hint）：**

```json
// ✅ 正确
{ "evidenceQuote": "主导 GPT-4 接入方案，3 个月上线", "status": "已满足" }

// ❌ 错误（概括改写）
{ "evidenceQuote": "候选人有 AI 产品经验", "status": "已满足" }

// ✅ 正确（无证据）
{ "evidenceQuote": "", "status": "待验证" }

// ❌ 错误（无证据但给高分）
{ "evidenceQuote": "", "score": 70, "status": "已满足" }
```

**已知局限（来自评测 Badcase）：**

1. 边界用例"只有 AI 关键词但无 AI 产品经验"：模型仍给 10-20 分（虽低，但理论上应为 0）
2. 推荐结论一致性 55%：即使证据不足，模型有时给"待人工确认"而非更明确的"暂不推荐"
3. 长噪音简历：大量无关文本会稀释核心缺失的显著性

**改进方向（v2）：**
- 在 Prompt 中加入"必备项中有任意一项无证据，推荐结论不得为推荐面试"（双重保护）
- 考虑 CoT 中间步骤：先列出所有有证据的事实，再评分（减少从印象出发）

### 2.4 面试题生成 Agent

```
你是结构化面试设计 Agent。
根据岗位能力模型、简历证据和人岗匹配缺口，生成 6 道不重复的面试题。
问题必须能让候选人给出具体事实，优先验证高权重要求、证据不足项和风险项。
不得询问年龄、婚育、健康、民族等与胜任力无关的信息。
```

**设计亮点：**
- "优先验证高权重要求、证据不足项和风险项"：给了明确的优先级，避免题目平均分布
- 合规约束显式写入：法律边界通过 Prompt 强制，而非依赖 HR 审查
- `relatedRequirementId` 字段：每道题必须关联具体要求，可追溯，不允许出现无关题

**面试题定制性评测结果：75%（目标 ≥ 80%）**

主要失分点：部分题目与候选人具体情况关联不够，更像通用面试题。
改进方向：Prompt 中加入"每道题必须引用候选人简历中的具体事实或差距"。

---

### 2.5 模拟回答 Agent

```
你是候选人模拟回答 Agent。
只能使用给定简历中明确存在的事实，生成普通但可信的第一人称回答。
不得虚构公司、项目、数字、职责或成果；
信息不足时应明确说无法从现有经历确认。
每个回答建议 120 到 220 个中文字符，并尽量按 STAR 结构表达。
```

**设计亮点：**
- "普通但可信"而非"优秀"：避免模型产生脱离简历的完美回答
- "120-220 字"：控制输出长度，接近真实面试回答长度
- "信息不足时明确说无法确认"：而非编造，保持简历事实边界

---

### 2.6 面试评估 Agent

```
你是企业招聘面试评估 Agent。
逐题评价回答的 STAR 完整度、与简历证据的一致性和专业深度。
不得因简历未披露的信息做负面推断。
发现回答超出简历证据时必须在 concerns 中指出。
回答很短或缺少事实细节时，应明确标记证据不足、降低结论置信度并建议追问，
不能把信息不足直接判断为能力不合格。
```

**设计亮点：**
- "不得因未披露信息做负面推断"：防止评估 Agent 因模拟回答信息少就打低分
- "降低置信度"而非"判断不合格"：区分"没说"和"能力不足"

## 3. 共通 Prompt 工程技术

### 3.1 修复重试机制

所有 Agent 都有自动修复重试：

```typescript
// 第一次失败时，携带校验错误信息重试
const repairInstruction = attempt > 0
  ? `上一次输出未通过结构校验。请只修复 JSON，不要解释。
     校验错误：${validationFeedback}
     上一次输出：${previousContent.slice(0, 12_000)}`
  : "";
```

**效果**：把结构校验成功率从约 88% 提升到约 99%（第一次失败后几乎都能在第二次修复）

### 3.2 Schema Hint 内嵌于 System Prompt

```typescript
// 而不是作为 user message 传入
messages: [
  { role: "system", content: `${system}\n只返回 JSON，不要添加 Markdown。\n输出结构：${schemaHint}` },
  { role: "user", content: safeUserContent }
]
```

**原因**：Schema 是 Agent 身份定义的一部分，放在 system 比 user 约束力更强。

### 3.3 隐私脱敏先于 Prompt 组装

```typescript
// model-client.ts
const safeUserContent = redactSensitiveText(options.user, "候选人").text;
```

脱敏在发送给任何 Agent 之前统一处理，不依赖各 Agent 自行处理。

## 4. Prompt 版本管理建议（v2）

当前 Prompts 集中在 `src/lib/agent/prompts.ts`，代码即版本。

v2 建议：
1. 在 `prompts.ts` 中为每个 Prompt 加 `version` 字段
2. 评测脚本记录使用的 Prompt 版本，便于追溯质量变化
3. 引入 A/B 评测框架：同一测试集对比两个版本，用 Judge LLM 评分

```typescript
export const matchPrompt = {
  version: "v1.2",
  lastChanged: "2026-08",
  changeReason: "加入关键词≠经验的显式约束，降低无证据高分率",
  system: "..."
};
```
